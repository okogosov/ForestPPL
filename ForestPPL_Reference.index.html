Introduction

ForestPPL Overview

ForestPPL is a console application developed in C++ using Microsoft Developer Studio, without relying on third-party packages. It operates on PPL.DLL, an implementation of the Parenthesis Programming Language (PPL). Originally written in C#, the PPL code was translated into C++.

PPL is an interpreted programming language in which all elements (statements, parameters, blocks) are enclosed in parentheses, resembling LISP syntax.

It includes a preprocessor to simplify code writing and reduce parentheses usage. PPL source code (format: .scr) is converted into an intermediate representation (format: .ppl) for immediate execution.

In this document, program text examples are shown as follows

PPL
>var x = 0
>d x

the results of running the examples are as follows

SCR
-----Variables  and arrays-----
-L0       x                             [0]

Sign > used as prompt in interactive mode.

Key features of PPL
Extensibility:

Combines C++ functionalities with custom user libraries by creating DLLs via the CodeGen.exe utility.

Enables adding full PPL functionality to any user application.

Modes:

ppl (base) mode: Syntax similar to LISP, using prefix notation for mathematical and logical expressions.

Examples
SCR
var (x [0]);
set(x) (+(1)(2));
set (x)( -(0)(+(3)(2)));  // infix notation: x = -(3 + 2);
if(==(x) (1)) …

scr (preprocessor) mode: Syntax similar to C, using infix notation for mathematical and logical expressions.

Examples
SCR
var x = 0;
set x = 1 + 2;  // or x = 1 + 2;
if (x == 1)…

Commands in format scr may be used on the left side of the expression

Parsing:

Code written in scr mode is translated into ppl mode before execution. Each parser level creates a syntax tree.

ForestPPL calls PPL API functions, which can also be used in other applications.

Execution Modes:

The operating mode (scr or ppl) is determined by the file extension or a command in the code itself.

scr mode simplifies coding by eliminating the need for enclosing statements in parentheses.

Default mode is set in Configuration.Data:(Code [ppl])

Scope Management (Scope Manager)

Introduction

ForestPPL utilizes a dedicated Scope Manager to handle memory allocation and variable lifecycles efficiently throughout the execution of a script.

Hierarchical Tracking: Maintains strict tracking of execution scopes, including Global, Local, Function, and Loop boundaries.

Variable Lifecycle: Handles the dynamic registration, lookup, modification, and safe removal of variables, constants, arrays, and complex structures.

Context Isolation: Ensures local function variables remain isolated while safely passing arguments and resolving pointers from caller to callee scopes.

Dynamic Parameter Binding: Supports advanced argument mapping across boundaries, including handling optional omitted parameters (using the # marker) and resolving loop counters.

Script Execution Stages

Script execution involves:

Creating an array of statements (simple or compound).

Generating a syntax tree for each statement.

Traversing all nodes in the syntax tree and executing the associated procedures.

Repeating the process recursively for each statement in compound blocks.

Continuing the process for each statement in the array until completion.

The dstree command allows users to visualize syntax trees for each script statement.

Debugging Features

ForestPPL includes commands for debugging:

dbg: Enables debugging mode.

traceppl: Traces code execution.

suspend and resume: Temporarily pauses script execution and resumes it.

start and stop: Measures the execution duration and outputs results in milliseconds.

On-the-fly code generation: The script can analyze data, collect new PPL commands from them (in the form of strings) and immediately execute them.

Dynamic patches: The ability to redefine variables, change constants or even operating logic right during program execution without restarting the kernel.

Interactive Debugging: If you want to make a REPL console (like Python or JavaScript) for your engine, a global eval like this would be the ideal heart of it, allowing the user to tamper with memory on the fly. ForestPPL doesn't treat programmers like children from whom sharp tools must be hidden. It grants absolute control over memory and code at runtime, trusting their expertise (see command "eval").Fundamentals

Identifiers and Scope Manager

Introduction

Names of nodes, variables, arrays, storage and functions contain any symbols, first symbol is any upper or lower case letter or any of the following symbols: _$# , but not a digit. Variables with first symbol "_" in name are hidden or private variables

A reserved name "result" is used for internal purposes in functions and cannot be used to create any variables.

Name "all" can not be used

Length of identifiers is not limited. Do not set keywords and names of Libraries as identifiers.

When data is created, its full name and saved address are added to Scope Manager.

TheScope Manager intelligently manages variable lifecycles, memory cleanup, and visibility boundaries, ensuring the safety and predictability of your code.

• Block-level scopes: Variables and arrays created within a block (such as a loop or conditional statement) exist only within that block. Upon exiting the block, all local variables are immediately and safely deleted from memory.

• Function isolation: Each function call creates a strict, isolated environment. Local variables defined within a function cannot conflict with variables in the parent code. This ensures function independence and the absence of side effects, while maintaining access to global variables.

• Intelligent variable overriding: Variable names may be safely reused. If a local variable has the same name as a global variable, the local variable temporarily "overrides" (replaces) the global variable within its specific block, without changing the original global data.

• Automatic conflict prevention: The engine performs instant, real-time checks when declaring new variables. This prevents accidental name conflicts within a single scope and ensures automatic memory resizing if a variable is intentionally re-created.

• No memory leaks: The user never has to manually delete variables. The Scope Manager tracks the exact lifecycle of each data structure and immediately frees memory upon scope exit.

Symbolic values are enclosed in quotation marks, to include a quotation mark in a symbolic expression, precede it with backslash.

printscope

Service Commands

The printscope command is an advanced debugging tool designed to inspect how the

interpreter manages memory and execution contexts at a system level.

What it does: When executed, this command queries the scopeManager directly and

outputs detailed, low-level information about the active scopes. It reveals the engine's

internal tracking of contexts and variable lifetimes.

How is it different from the d (display) command? It is important to understand the

distinction between these two debugging tools:

d (display): This is a user-facing command. It visually renders the hierarchical syntax

tree (NS -> Global / Local) and shows the declared variables alongside their current

values.

printscope: This is an engine-facing command. It focuses on the mechanics of the

scopeManager, revealing the underlying stack architecture, particularly how execution

contexts are pushed and popped during function calls.

When to use it: The printscope command is highly valuable when debugging complex

UserFunctions. It allows you to verify that local contexts are properly isolated,

arguments are correctly passed, and that the scopeManager is accurately cleaning up

memory upon returning from nested blocks of code.

Format: printscope

Examples
PPL
>var x
>createnode N1
>var N1.x
>array N1.arr[5]
>printscope
SCR
=========== State of SCOPE MANAGER ===========
Depth [0]
 (Global)
 <-- TOP (Current of Context)
SCR
    * empty
    * x
    * N1 = 'node Node'
    * N1.x
    * N1.arr = 'array N1.Array 5'

sdimsize

Storage

Returns the number of children (size) of the storage node

reached by following a path of branch indices from the root.

PPL SYNTAX
sdimsize(name)[(idx1)(idx2)...(idxN)][(out_var)]

Semantics:

- No indices -> size of the top-level dimension (axis 0),

i.e. how many slices/branches the storage has at its root.

- Each additional (idxK) descends one level further, into

the child at that index, and returns THAT node's size.

- Because storages can be jagged (see sresize), a path of

the same length can return different sizes depending on

which branch you follow -- there is no single global

"size of axis N" once branches have been resized

independently.

- If the last argument is not a number, it is taken as

out_var and the result is also written into that

variable (same effect as a separate assignment).

Limitation: dimension_index arguments must be literal integers

or already-evaluated expressions; a math expression that can't

be resolved to an int is not accepted here.

Error: if the path is invalid (out of bounds, or descends into

a leaf), sdimsize reports an error instead of returning -1

silently.

PPL
>storage s3[3,4,5];
>var x;
>x = sdimsize(s3);         // top level -- axis 0

>x = sdimsize(s3)(0);      // descend into branch 0 -- axis 1

DataFrame is a table with named columns, columns may be defined with different types,number of rows and columns is not limited.

DataFrame Architecture in Forest (Under the Hood)

When you create or load a DataFrame in Forest, the engine builds a highly optimized Abstract Syntax Tree (AST) structure designed for both execution speed and memory efficiency. The engine uses a hybrid approach, separating global script variables from internal metadata.

Here is how a DataFrame is structurally organized inside the engine:

Root Node (DataFrame): The parent object representing the table (e.g., DF1). This node is explicitly registered in the engine's global cache (ScopeManager), allowing the script to find the table instantly via an O(1) or highly optimized lookup.

Settings Node (Settings): A private, internal branch directly attached to the root. It acts as a container for all table metadata, such as RowsLength, PrintEmptyRows, and specific column formats (Type and Width). To maximize performance and prevent polluting the global memory space, Settings and its children are not registered in the global cache. The core engine accesses them directly via rapid tree traversal.

Data Columns (Arrays): The actual data vectors (e.g., DF1.Name, DF1.Quantity). These are stored as dedicated array nodes under the root. Because scripts often need direct and fast access to these columns, they are registered in the global cache alongside the root node.

Why this matters for performance:

By keeping internal settings encapsulated within the AST and only exposing the Root and Column arrays to the global ScopeManager, Forest maintains a minimal memory footprint. This architecture guarantees that even with hundreds of loaded dataframes, variable lookups remain lightning-fast.

The StorageLib library provides methods for creating and manipulating dynamic storage collections (arrays/lists). This library uses the names created by the storage command, so storagename is not enclosed in quotes.
